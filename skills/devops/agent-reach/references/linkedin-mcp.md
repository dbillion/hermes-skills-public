# LinkedIn MCP Server (linkedin-scraper-mcp) — setup & pitfalls

## What it is
Agent Reach's LinkedIn channel is backed by `linkedin-scraper-mcp` (PyPI package
renamed to `mcp-server-linkedin`). It is a standalone MCP server, launched
separately, and registered with mcporter. NOT served by OpenCLI.

## Install
```
pip install linkedin-scraper-mcp        # v4.14.0 at time of writing
# binaries: <venv>/bin/linkedin-scraper-mcp  (forwards to mcp-server-linkedin)
#           <venv>/bin/mcp-server-linkedin
```

## Session storage (server-managed)
- Cookie file: `/home/deeone/.linkedin-mcp/cookies.json`
  FLAT list of cookie dicts:
  `[{name, value, domain, path, expires, httpOnly, secure, sameSite}]`
  — NOT `{"cookies":[...]}`. import_cookies() iterates the list directly.
- Source state: `/home/deeone/.linkedin-mcp/source-state.json`
  needs `source_runtime_id` + `login_generation`; generated by the server's own
  `write_source_state()`. get_authentication_source() requires BOTH files to exist.
- import_cookies() filters to a preset subset (li_at, JSESSIONID, bcookie,
  bscookie, lidc, ...) and REQUIRES `li_at` or it returns False.

## AUTH: the ONLY reliable path is first-party `--login`
```
linkedin-scraper-mcp --login
```
- Opens a REAL browser window in the server's own browser context.
- User logs in (email/password + 2FA/captcha handled in-window).
- Session saved natively, persists. Server exits; then launch HTTP server.

WHY NOT cookie injection / CDP extraction:
- Launching a second Chrome with `--remote-debugging-port=9222
  --user-data-dir=<copy of profile>` and reading cookies via a Python
  `websockets` client DOES return `li_at` (HttpOnly) decrypted from memory.
- BUT when the LinkedIn server replays that cookie in its own isolated
  Chromium, LinkedIn redirects /feed/ → /login/ (cross-context / session-binding
  protection). Server logs:
  `Feed auth check failed ... auth blocker URL: https://www.linkedin.com/login/...
   Stale session detected; triggering re-login.`
  The injected session is rejected.
- Conclusion: use `--login` (first-party). CDP extraction is a dead end for
  LinkedIn.

## Launch HTTP server (after login)
```
linkedin-scraper-mcp --transport streamable-http --host 127.0.0.1 --port 3000 \
  --log-level WARNING
```
Verify reachability:
```
curl -s -o /dev/null -w "%{http_code}" http://127.0.0.1:3000/mcp
# 406 is expected for a bare GET on the streamable-http endpoint.
```

## Register with mcporter (CWD matters!)
```
cd /home/deeone            # REQUIRED. Real config: /home/deeone/config/mcporter.json
mcporter config add linkedin http://127.0.0.1:3000/mcp
```
Verify:
```
mcporter config list
# linkedin should appear under: Project config: /home/deeone/config/mcporter.json
```
Calling `mcporter` from a different CWD (e.g. /tmp) writes to a STRAY project
config and later calls fail with `Unknown MCP server 'linkedin'`. Remove strays.

## Verify session
```
mcporter call 'linkedin.get_my_profile()'
# → returns YOUR linkedin.com/in/<you> with followers/about/activity.
```

## Tools (read + network only — NO apply)
- `get_my_profile()`, `get_person_profile(linkedin_username, sections?)`
- `search_people(keywords, location?, network?, current_company?)`
- `search_jobs(keywords, location?, easy_apply?:bool, max_pages?, date_posted?)`
- `get_job_details(job_id)`, `get_saved_jobs()`
- `get_company_profile`, `get_company_posts`, `get_company_employees`,
  `search_companies`
- `get_sidebar_profiles`, `get_inbox`, `get_conversation`, `search_conversations`,
  `send_message`, `connect_with_person`
- NO Easy-Apply submit / form-fill / CV upload. Automated applying is against
  LinkedIn ToS and a ban risk — do read-only shortlists, let the user click apply.

## Pitfalls recap
- Server dies with the terminal session → make it persistent (systemd user
  service / launchd / restart-on-exit wrapper) if you want it to survive.
- `--status` showing "foreign runtime (fresh bridge each startup)" means a derived/
  bridged cookie, not a fresh first-party login → will go stale fast. Do a clean
  `--login` to fix.
- Config fragmentation: ensure exa + linkedin both live in
  /home/deeone/config/mcporter.json; delete stray copies elsewhere.
- The separate `twitter` CLI binary failing with "cookie extraction failed /
  keyring" is IRRELEVANT — agent-reach uses OpenCLI's twitter, which works off the
  Chrome login state. Don't conflate the two.
